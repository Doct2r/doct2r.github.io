메모리를 사람이 직접 잡고 놓아주면, 그렇게 하지 않는 자동화된 방식(가비지 컬렉션)보다 항상 빠를까. 흥행 여부나 언어의 인기와 무관하게, 순수하게 성능만 놓고 보면 답은 직관과 다르다. 이 글은 이 질문을 정면으로 실험한 두 편의 저명한 컴퓨터과학 논문을 통해 답을 찾는다.

---

## 1. 2005년 하츠-버거 연구 — 관건은 "누가 하느냐"가 아니라 "메모리가 얼마나 있느냐"

가비지 컬렉션(GC)과 명시적 메모리 관리(사람이 직접 free를 호출하는 방식)를 공정하게 비교하기는 원래 어려웠다 — 자바처럼 GC를 전제로 설계된 언어의 코드에는 애초에 free 호출 자체가 없기 때문이다. 매튜 하츠와 에머리 버거는 2005년 OOPSLA에서 이 문제를 우회하는 새로운 실험 방법론을 제시하며 둘을 직접 비교했다.

결과는 이랬다 — 사용 가능한 메모리를 실제 필요량의 3배로 넉넉하게 주면, GC는 명시적 메모리 관리보다 평균 17%밖에 느리지 않았다. 그런데 메모리를 2배로 좁히면 GC의 성능이 거의 70% 나빠졌고, 물리 메모리 자체가 부족해 페이징이 발생하는 상황에서는 GC가 명시적 관리보다 자릿수 단위로(수십 배) 느려졌다. 이 결과가 말하는 건 단순하다 — "메모리를 누가 관리하느냐"보다 "메모리가 얼마나 넉넉한가"가 성능을 가르는 더 결정적인 변수라는 것이다.

## 2. 왜 자동 할당이 원천적으로 빠를 수 있는가

이 결과에는 기술적 이유가 있다. 세대별(generational) GC가 흔히 쓰는 "범프 할당(bump allocation)"은 빈 공간을 찾아 헤매는 malloc의 프리 리스트 탐색과 달리, 포인터를 그냥 앞으로 미는 것만으로 할당을 끝낸다 — 범프 포인터 할당을 쓰는 치니의 알고리즘이 마크-스윕 방식보다 할당 속도에서 4배 빠르다는 연구 결과도 있다. 여기에 압축형(compacting) GC는 살아남은 객체를 촘촘하게 재배치해 캐시 지역성을 오히려 개선하는 반면, 사람이 직접 관리하는 할당자는 이미 할당된 객체를 마음대로 옮길 수 없어 크기별로 나눈 빈(bin)이나 재할당 트릭에 의존할 수밖에 없다. 할당이 잦아질수록 세대별 GC가 일반적으로 더 나은 성능을 보인다는 연구 결과도 이런 구조적 이유에서 나온다.

## 3. "결정론적"이라 유리해 보이는 참조 카운팅의 함정

애플의 ARC(자동 참조 카운팅) 같은 방식은 객체가 참조를 잃는 순간 즉시 해제된다는 점에서 언뜻 GC보다 예측 가능하고 빨라 보인다. 그런데 실제 연구에서, 참조 카운팅 연산 전체를 원자적(atomic) 방식에서 비원자적 방식으로만 바꿔도 마이크로벤치마크에서 최대 220%, 벤치마크게임에서 120%, 리처즈 벤치마크에서 70%의 속도 향상 여지가 확인됐다. 이는 참조를 주고받을 때마다 카운트를 증감시키는 연산 자체의 비용이 상당하다는 뜻이다. 게다가 GC는 필요 없어진 객체들을 한꺼번에 일괄 처리할 수 있지만, 참조 카운팅은 객체 하나하나를 개별적으로 관리해야 해서 대량 삭제가 몰릴 때 오히려 효율이 떨어진다.

## 4. 장기 실행 프로그램을 갉아먹는 파편화

수동 할당·해제를 오래 반복하면 사용 가능한 메모리가 작은 조각들로 쪼개지는 파편화가 쌓인다. 실제 사례로, 24시간 연속 실행 후 처음엔 1초 걸리던 동일한 작업이 7초로 늘어난 경우가 보고돼 있다 — 파편화가 누적된 결과였다. 짧게 실행되고 끝나는 프로그램에서는 문제가 되지 않지만, 오래 켜 두는 프로그램에서는 이 파편화 자체가 수동 관리의 발목을 잡을 수 있다.

## 5. 2002년 버거-존-매킨리 연구 — 직접 짠 최적화 코드 대부분이 실패했다

가장 직접적인 답은 2002년 에머리 버거·벤저민 존·캐서린 매킨리의 연구에서 나온다. 이들은 프로그래머가 성능을 높이겠다고 직접 작성한 "커스텀 메모리 할당자"를 쓰는 애플리케이션 8개를 조사했다. 결과는 통념과 반대였다 — 8개 중 6개에서, 잘 만들어진 범용 할당자(리 할당자)가 프로그래머가 직접 짠 커스텀 할당자와 같거나 더 나은 성능을 보였다. 즉 "우리 프로그램에 맞춰 직접 최적화했다"고 믿었던 코드 대부분이, 실제로는 검증된 범용 도구를 이기지 못했다는 뜻이다. 이 논문은 2012년 "OOPSLA 최고 영향력 논문"으로 선정될 만큼 이 분야에 영향을 미쳤다.

예외는 있었다 — 영역(region) 기반 할당자를 쓴 두 애플리케이션은 실제로 최대 44%의 성능 향상을 보였다. 다만 이 방식은 개별 객체를 따로 해제할 수 없어 메모리 사용량이 크게 늘어날 수 있다는 대가가 따랐다.

## 6. 그렇다면 언제 수동 관리가 진짜로 이기는가

최근 연구들은 이 예외를 더 구체화한다 — 아레나(범프) 할당자는 전형적인 워크로드에서 범용 할당자보다 2~5배 빠른데, 이 이득은 할당 횟수가 많을수록 커지고 할당 크기가 클수록 줄어든다. 이 방식이 특히 잘 맞는 경우는 파서·컴파일러·가상머신·게임 엔진처럼, 수명이 비슷한 작은 객체 여러 개가 한꺼번에 태어나고 한꺼번에 죽는 패턴이 뚜렷할 때다. 즉 수동 관리가 이기는 지점은 "무조건"이 아니라, 데이터의 생애 주기 패턴을 정확히 알고 그 패턴에 맞춰 설계했을 때로 좁게 한정된다.

## 정리

"사람이 자원을 직접 관리하면 무조건 좋아지는가"라는 질문에 두 편의 저명한 논문이 실증적으로 답했다 — 아니다. 메모리가 넉넉하면 GC와 명시적 관리의 격차는 17%까지 좁혀지고(하츠-버거, 2005), 프로그래머가 직접 짠 범용 목적의 커스텀 할당자 대부분은 잘 만든 범용 할당자를 이기지 못했다(버거·존·매킨리, 2002). 수동 관리가 실제로 이득을 보는 지점은 뚜렷하다 — 아레나·범프 할당처럼 데이터의 생애 주기 패턴을 정확히 파악하고 그에 맞춰 설계했을 때뿐이다. 수동 자원 관리는 성능의 상한선을 끌어올려 주지만, 그 상한선에 실제로 도달하느냐는 완전히 다른 문제이며, 검증되지 않은 대부분의 실전 코드는 그 상한선 근처에도 가지 못한 채 오히려 잘 만든 범용 도구보다 못한 결과를 낸다는 게 두 연구가 공통으로 보여주는 그림이다.
