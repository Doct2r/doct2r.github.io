"요즘은 클래스 상속이 단점으로 취급받는다"는 인상은 Go·Rust 같은 신생 언어가 상속을 아예 없애고, Swift가 "프로토콜 지향"을 내세우면서 최근 몇 년 사이 굳어진 것처럼 보인다. 그런데 실제로 뒤져보면 이 비판은 최근에 생긴 게 아니다. 객체지향이라는 용어를 만든 사람 본인부터, GoF 디자인 패턴 저자들 자신까지 — 상속의 위험성은 처음부터 알려져 있었다. "요즘 의견이 많다"는 인상은 오래된 이론적 경고가 언어 설계 차원의 실제 배제로 뒤늦게 가시화된 결과에 가깝다.

## 1. 알란 케이 — "객체지향"을 만든 사람은 상속을 강조하지 않았다

"객체지향(object-oriented)"이라는 용어 자체를 만든 앨런 케이는 1997년 OOPSLA에서 이렇게 말했다. "내가 객체지향이라는 용어를 만들었고, C++를 염두에 둔 게 아니었다고 분명히 말할 수 있다." 1998년 이메일에서는 한발 더 나가 이 개념의 핵심을 다시 정의했다 — "객체는 오해를 부르는 이름이었고, 더 적절한 용어는 '메시징(messaging)'이었을 것"이라며, 자신이 스몰토크를 설계할 때 떠올린 이미지는 "생물학적 세포, 또는 네트워크상의 개별 컴퓨터들처럼 메시지로만 소통하는 것"이었다고 밝혔다. 즉 케이가 강조한 OOP의 핵심은 캡슐화된 단위들 사이의 메시지 교환이었고, 클래스 계층을 타고 코드를 재사용하는 상속은 원래 구상의 중심이 아니었다.

## 2. 학계는 1980년대부터 이미 경고했다

**요요 문제(Yo-yo Problem, 1989)**: 데이비드 텐저(Taenzer)·간티(Ganti)·포다르(Podar)가 1989년 「Object-Oriented Software Reuse: The Yoyo Problem」에서 처음 이름 붙인 문제다. 상속 계층이 깊어지면, 어떤 메서드가 실제로 어느 클래스에서 실행되는지 추적하기 위해 계층을 위아래로 계속 오르내려야 한다 — 저자들은 "마치 요요를 타는 느낌"이라고 표현했다.

**리스코프 치환 원칙(1987)**: 바버라 리스코프가 1987년 OOPSLA 키노트 "Data Abstraction and Hierarchy"에서 제시한 원칙이다. "타입 S의 객체 o1이 있을 때, T의 모든 프로그램 P에서 o1로 T의 객체 o2를 대체해도 P의 행동이 바뀌지 않는다면, S는 T의 서브타입이다." 겉보기엔 단순한 문법적 요구지만, 실무에서 상속으로 만들어진 서브클래스 대부분이 이 행동적 조건을 실제로 만족하는지는 별개 문제다 — "펭귄은 새다, 그런데 새는 날 수 있다" 같은 흔한 반례가 이 원칙이 왜 필요한지를 보여준다.

**취약한 기반 클래스 문제(Fragile Base Class Problem, 1998)**: 미하일로프(Mikhajlov)와 세케린스키(Sekerinski)가 1998년 ECOOP에서 발표한 「A Study of The Fragile Base Class Problem」이 이 문제에 공식 이름을 붙였다. 기반 클래스를 개발한 사람이, 그 클래스를 상속해 확장한 다른 개발자의 코드를 전혀 모른 채 기반 클래스를 "합리적으로" 수정하면, 그 수정이 자식 클래스를 깨뜨릴 수 있다는 것이다. 논문은 이를 "유연성(flexibility) 속성"으로 정식화하고, 다섯 가지 독립적인 예시로 문제의 여러 양상을 증명했다.

## 3. GoF 자신도 이미 알고 있었다

1994년 에리히 감마·리처드 헬름·랄프 존슨·존 블리시디스(GoF)가 쓴 [《디자인 패턴》](/posts/design-patterns/)에는 "객체 합성을 클래스 상속보다 선호하라(Favor object composition over class inheritance)"는 원칙이 명시돼 있다. 상속 다음으로 다뤄지는 두 번째 객체지향 설계 원칙으로, 한 페이지 반에 걸친 근거 설명 뒤에 나온다. 아이러니한 점은, 이 원칙을 써놓은 바로 그 책에 실린 GoF 23개 패턴 다수가 상속을 전제로 설명된다는 것이다 — Template Method는 상속으로 알고리즘 뼈대를 고정하는 패턴이고, Decorator는 정확히 "상속 없이 기능을 덧붙이려면"이라는 문제의식에서 나왔다. 즉 GoF는 상속의 위험을 알면서도, 당시 주류였던 C++/스몰토크 생태계 안에서 상속과 합성을 함께 다루는 절충적 태도를 취했다.

## 4. 업계 표준 조언으로 굳어지다

조슈아 블로크(Joshua Bloch)의 《Effective Java》(2001년 1판) Item 16 "합성을 상속보다 선호하라"는 이 원칙을 실무 스타일 가이드 차원으로 끌어내린 대표적 사례다. 블로크는 상속이 "캡슐화를 위반한다"는 점을 핵심 근거로 든다 — 서브클래스의 동작이 슈퍼클래스의 구현 세부사항에 의존하게 되고, 슈퍼클래스가 다음 릴리스에서 바뀌면 서브클래스가 아무것도 고치지 않았는데도 깨질 수 있다(취약한 기반 클래스 문제의 실무 버전이다). 블로크의 대안은 상속 대신 필드로 다른 클래스의 인스턴스를 갖고 그 메서드를 위임(forwarding)하는 것이었고, 상속은 "진짜 is-a 관계가 성립할 때만" 쓰라고 못박았다.

## 5. 언어 설계가 실제로 상속을 배제하기 시작하다

이론적 경고와 스타일 가이드 권고를 넘어, 언어 자체가 상속을 구조적으로 제한하거나 없앤 사례들이 있다.

**다중 상속과 다이아몬드 문제**: 클래스 D가 클래스 B와 C를 상속하고, B와 C가 공통으로 클래스 A를 상속하면 D가 A의 메서드를 어느 경로로 물려받을지 모호해진다. 자바의 리드 설계자 제임스 고슬링은 1995년 백서에서 "자바는 C++의 드물게 쓰이고 잘 이해되지 않는, 혼란만 주는 기능들을 생략했다"며 연산자 오버로딩과 다중 상속을 명시적으로 꼽았다. 대신 자바는 오브젝티브-C의 프로토콜 개념을 빌려온 인터페이스를 통해 "다중 인터페이스 상속"만 허용하는 절충안을 택했다 — 메서드 시그니처는 여럿 물려받되 구현 충돌은 원천적으로 생기지 않게 한 것이다.

**Go(2009) — 클래스 자체가 없다**: Go는 클래스도, 전통적 의미의 상속도 없다. 대신 구조체 안에 다른 구조체를 익명 필드로 끼워 넣는 임베딩(embedding)과, 덕 타이핑에 가까운 인터페이스로 재사용을 해결한다. 롭 파이크는 이를 두고 Go에도 "상속과 유사한 것"이 있지만 C++식 서브타입 폴리모피즘과는 다르다고 설명했다 — 임베딩은 타입 시스템의 다른 요소들과 직교(orthogonal)하도록 설계된 별개의 개념이다. 이는 실수로 빠진 기능이 아니라, 상속이 낳는 문제들을 수십 년 겪은 뒤 세 명의 설계자(파이크·로버트 그리즈머·켄 톰프슨)가 의도적으로 합의한 결정이었다.

**Rust — 상속이 없다**: Rust에는 `extends`도, 베이스 클래스도, 가상 메서드도, 숨겨진 슈퍼 호출도 없다. 큰 구조체는 작은 구조체들을 필드로 담아 조립하고, 공유 동작은 트레이트(trait)·제네릭·매크로로 구현한다. 상속을 없앤 대가로 다이아몬드 문제 자체가 원천적으로 사라지고, 서브클래스가 부모의 내부 상태를 암묵적으로 물려받는 일도 없어 소유권·캡슐화가 명시적으로 유지된다 — 이는 Rust가 강조하는 안전한 동시성 코드 작성에도 직접 도움이 된다.

**Swift(2015) — 프로토콜 지향 프로그래밍**: 스위프트 표준 라이브러리 기술 리드였던 데이브 에이브러햄스는 WWDC 2015 세션 408 "Protocol-Oriented Programming in Swift"에서 "스위프트는 근본적으로 프로토콜 지향 언어"라고 선언했다. 상속을 아예 없애진 않았지만, 프로토콜 확장(protocol extension)으로 기본 구현을 제공하는 방식을 앞세워 클래스 상속을 우선 선택지에서 밀어냈다.

## 정리

```
1987  리스코프 치환 원칙 — "행동이 바뀌지 않아야 서브타입" 이론적 기준 제시
1989  요요 문제 명명 — 깊은 상속 계층을 오르내리며 코드를 추적하는 피로
1994  GoF 「디자인 패턴」 — "합성을 상속보다 선호하라" 원칙 자체 명시 (그러나 패턴 다수는 상속 전제)
1995  제임스 고슬링 — 자바에서 다중 상속 배제, 인터페이스로 절충
1997  앨런 케이 — "C++를 염두에 둔 적 없다", OOP 핵심은 메시징이라 재정의
1998  취약한 기반 클래스 문제 — 기반 클래스 수정이 자식을 깨뜨리는 구조 정식화
2001  조슈아 블로크 「Effective Java」 — 캡슐화 위반을 근거로 합성 권고를 업계 표준화
2009  Go — 클래스·상속 자체를 언어에서 제거, 임베딩+인터페이스로 대체
2015  Swift — "프로토콜 지향 언어" 선언
2010년대~  Rust — 상속 없이 트레이트+제네릭으로 합성
```

"요즘 상속이 단점으로 여겨진다"는 인상은 최근 몇 년의 새로운 발견이 아니라, 1987년부터 이어진 이론적 경고가 2009년 이후 신생 언어들의 설계 결정으로 하나씩 실현되며 점점 눈에 보이게 된 결과다. GoF조차 1994년에 이미 합성을 선호하라고 써놓았다는 사실이 보여주듯, 문제는 답을 몰랐던 게 아니라 C++·자바 같은 주류 언어가 오랫동안 상속을 문법적 기본값으로 유지해왔다는 데 있었다. 그 기본값이 바뀌기 시작한 게 지금이라는 것뿐이다.
